| `CFG_TURN_CONFIRM_FAST_MS` | **40 ms** | 偏着丢（直角弯） |
| `CFG_BLIND_ARM_MS` | 120 ms | 居中丢（断口/反光），保持不变 |

## P0.2 "能不能纯循迹 + PID 过直角？"（2026-11-25 结论 + 实施）

### 结论：不能。原因是几何，不是调参

纯 PID 要让车跟着线转 90°，车就必须走一段圆弧。圆弧半径 R = v / ω：

| 条件 | 数值 | 来源 |
|---|---|---|
| 实车转弯角速度 | **ω ≈ 93 °/s（1.63 rad/s）** | run_215809：105° / 1.126 s |
| 转弯时前进速度 | v ≈ 76 mm/s | 同段 dist 86 mm / 1.126 s |
| 因此半径 | **R = 47 mm** | 76 / 1.63 |
| 300 mm/s 时同样 ω 的半径 | **R = 184 mm** | 300 / 1.63 |
| 8 路视野半宽 | **35 mm** | 70 mm / 2 |

也就是说：在 300 mm/s 上，纯 PID 必须让车横向漂 **184 mm** 才能把 90° 转完，
而传感器只看得见 **35 mm**。转到 1/5 的时候线就出视野了，PID 没有输入，
剩下 70° 是开环滑过去的 —— 比现在的状态机更不可控。

反过来算：要把 R 压进 35 mm，速度只能到 **57 mm/s**（ω=93°/s）或 **122 mm/s**
（ω 按差速极限 200°/s 算）。当前过弯平均就有 ~96 mm/s，**纯 PID 只会更慢**。

> 所以"纯循迹 PID 过直角"在这套硬件上不成立。真正的毛病不是 PID 不够猛，
> 而是**开转的时机**。下面这条改动就是修时机。

### 真因：开转比拐点晚 153 mm（实测）

run_215809 第 1 个弯的原始帧：

```
4.189  dist=2450  raw=E0  cnt=5  err=+1   ← 线"变宽"：车正压在拐点上
4.293  dist=2481  raw=F7  cnt=1  err=0
4.596  dist=2573  raw=FF  cnt=0           ← 彻底丢线
4.700  dist=2603                          ← EL_TURN90 才开始转
```

从拐点（2450）到真正开转（2603）**晚了 153 mm / 约 500 ms**。这段由三部分组成：

| 段 | 时间 | 说明 |
|---|---|---|
| 等丢线 | ~100 ms | 线从 cnt=5 塌到 0 的过程 |
| 丢线确认 | 120 ms | `CFG_BLIND_ARM_MS` |
| 刹车相 | 80 ms | `g_turn_brake` |

### 连带后果：过冲和"转角总是 105°"是同一件事

车带着 60 mm 过冲进入旋转 → 转满 90° 时，新线已经在车身侧向 60 mm 处
（> ±35 mm 视野）→ 看不见 → 继续转到 105° 才让线露在视野边缘 →
`[turn] done` 总是 104~105 → 转完 `cnt=1` → 再走 100 mm 丢线 → SEEK 失败停车。

**这就是"冲出去才转"和"转完就丢线"的同一个根。** 修好时机，两个一起好。

### 改动（`ctrl_fsm.c` + `app_config.h`）

**触发信号换成"线变宽"**（不再只靠 |err|）：

```c
edge = |err| >= CFG_PRE_TURN_ERR(2.0)      /* 线偏到边缘：斜着进弯的场子 */
wide = trk->count >= CFG_PRE_TURN_CNT(5)   /* 线变宽：直角弯压在拐点上 */
```

`wide` 为什么可靠：正常循迹只有 2~3 路压线；5 路只可能是"来路 + 去路两条胶带
同时压在传感器上"，那就是拐点。而这时 `err` 只有 ±1 —— **只看 err 永远等不到**。

配套四处：

| 项 | 值 | 理由 |
|---|---|---|
| `CFG_PRE_TURN_ENABLE` | 0 → **1** | 重新打开，但走 wide 那条路 |
| `CFG_PRE_TURN_BRAKE_MS` | 新，**50 ms** | 完全不刹时轮速要跳变 700 mm/s，电机跟不上、每次滑行距离不同（这是 brake=0 时转角离散 37° 的由来）；50 ms 只花 15 mm |
| `CFG_TURN_EARLY_MIN_DEG_PRE` | 新，**85°** | 从拐点起转只要 ~90°；沿用 95° 会白转 5°。低于 80° 又会被"来路旧线"骗着提前收手 |
| 中止判据 | 仅 edge 触发时生效 | wide 触发说明车就在拐点上，此时"线还居中"是正常的，不能当中止依据 |
| 环岛区 | `loop_zone` 时禁用提前入弯 | 六边形入口同样"线变宽"，但它要进环岛不要转 90° |

日志新增 `w=1`（`[turn] #n/N seq pre=1 w=1`）：标明这次是 wide 触发的。

### 验收（方场 4 个弯，每趟 ~15 s）

1. `[turn] ... pre=1 w=1` —— 说明是 wide 触发的；
2. `[el] 12` 的 `dist` 比"最后见线"**提前**，而不是落后（对比 2450 vs 2603）；
3. `[turn] done` 从 104~105° 降到 **88~95°**；
4. 转完 `[el] 13` 那拍 `cnt` 应为 **2~3**（线在中间），不再是 0~1；
5. 4 个弯连续过、不停车。

## P0.4 曲线 / 圆形环岛被误判成直角弯（2026-11-25 22:23，run_222323）

### 数据：三次提前入弯，两次是误判

```
0.53  el=9   dist=41                ← 起跑黑带（路口）
2.08  el=12  dist=537  cnt=5 raw=E0 → 右转 -91.4°  ✅ 真直角
4.16  el=12  dist=980  cnt=0 raw=FF → 左转 +85.4°  ❌ 圆形环岛岔口
7.83  el=12  dist=1938 cnt=2 raw=9F → 左转 +104.2° ❌ 弯道（车偏 20 mm）
```

三次都是 `pre=1 w=0` —— **全是 edge（|err|≥2.0）触发的**，wide 一次都没触发。

### 根因：edge 把"曲线"认成了"直角弯"

`#3` 是最干净的反例：**只有 2 路压线**（单条胶带，车在曲线里偏到一侧 20 mm），
`err` 到了 2.0 就判成直角弯。曲线行驶、圆形环岛、S 弯全是这种形态 ——
它们本来就是"单条胶带 + 车暂时偏一侧"，err 必然到 2.0。

而真直角弯（`#1`）是 **`cnt=5 raw=E0`**：来路和去路两条胶带叠在一起。
**"线偏了"和"两条线叠了"是两件事，edge 只看到前者。**

### 改动

| 项 | 内容 |
|---|---|
| `CFG_PRE_TURN_EDGE_EN = 0` | edge 单独触发被关闭（宏留着，换赛道可开） |
| 提前入弯只认 `wide` | `cnt >= CFG_PRE_TURN_CNT(5)` |
| 日志加 `c= e=` | `[turn] ... pre=1 w=1 c=5 e=150`，一眼分辨触发形态 |
| `[tr]` 跟踪覆盖 `el=2` | 原来只对 3/5/6/7 开，曲线段（2→3→2）一条细数据都没有 |

代价：某个弯若压得不够正、只到 4 路，就退回"丢线才转"的老逻辑 ——
慢 150 mm 但不会转错。**错一次出赛道，慢一次只是慢。**

### 下一趟要看的

1. 7 个真直角弯的 `[turn]` 是否都是 `w=1 c>=5`（若出现 `pre=0`，说明它没到 5 路，
   退回老逻辑了 —— 看 `dt` 会涨到 850~1000）；
2. 曲线段 / 圆形环岛段**不应再出现** `[el] 12`；
3. 新加的 `[tr]` 数据能直接看到曲线段的 `cnt/err` 形态，用于下一步收紧判据。

> 如果发现圆形环岛的**岔口**（两条胶带分开处）也产生 `cnt>=5`，
> 那就得再加一条"必须随后丢线才算弯"的确认 —— 但现在先让数据说话。

## P0.5 环岛"有时进、有时直着过去" + 绕完之后的连锁崩坏（2026-11-25 22:38）

### 现象（用户现场）
run_223758 这一趟：状态机进了 `el=6/7`，但**车实际是沿切线直着开过去的**，没绕六边形。
绕"完"（其实是走完 1.78 m 直线）出来丢线，被判成直角弯转了 105.6°，车扔出赛道，
接着又误进一次环岛，最后复位 —— 整趟报废。

### 为什么时灵时不灵：入口靠的是"横向偏置"，它不能转弯

地图放大确认：**六边形的右侧顶点是单点贴在主线上的**。车沿切线走时，顶点处看到
4~6 路宽黑，位置环误差≈0，`e_bias=2.5` 只能让车**平移** 20~30 mm，
**不足以咬住六边形第一条边**（那条边与切线夹角 60°）。

两次跑同一个岔口的数据几乎一样（都 `cnt=5~6`），一次进、一次不进 ——
差别只在"车在岔口那一瞬的横向位置"。**这本质上是碰运气，不是判据问题。**

### 改动

| # | 内容 |
|---|---|
| 1 | **入口强制转 `CFG_LOOP_ENTRY_DEG=60°`**：`EL_LOOP_IN` 用陀螺仪转到 `入口航向 ± 60°`，转到位（±8°）再进 `LOOP_RUN` 跟线。六边形内角 120° ⇒ 相邻边夹角 60°，从切线转 60° 正好落在第一条边上 |
| 2 | 转角累计是全局的（`s_yaw_acc` 在入口清零），这 60° 会计入 360°，不会多绕 |
| 3 | 入口里程上限 `CFG_LOOP_ENTRY_MM=300`：万一转不到位也不会卡死 |
| 4 | **绕过环岛后禁止再判直角弯**（`s_loop_done`）：丢线改走 `EL_SEEK`。赛道最后一个环岛之后只剩终点，不可能再有直角弯。**宁可慢，不许转错** |
| 5 | 修日志：`pre=0` 时 `c=0 e=0`（之前在丢线转弯时残留上一弯的旧值） |

`CFG_LOOP_ENTRY_DEG = 0` 可退回旧的偏置方式。

### 测试方法（不用跑整圈）
车放**断口出口后 20~30 cm**（岔口前约 1 m）→ 抓 `N 1` → `a`。一段约 15 s。
验收：`[el] 6` 之后 `yaw` 应**先跳 60°**，然后 `el=7` 持续约 9~11 s、`yaw` 累计 360°，
最后 `el=8 → 2`。若 60° 转进去后压不到边线（`[el] 7` 里 `cnt` 长期为 0），
说明角度不对，按 30° 一档试（45/75）。

### P0.5.1 实测：强制 60° 生效了，但**方向反了**（run_225036）

```
10442  el=6  yaw=-92
10540  el=7  yaw=-152    ← 确实转了 60°（强制入环逻辑生效）
10644  ...   yaw=-133    ← 立刻被拉回
11284  el=8  yaw=-97     ← 完全回到原航向：等于没进去
```

**根因**：`CFG_LOOP_EDGE_DIR = +1`（右）是当年给 `e_bias`（横向偏置）用的符号。
那时候方向其实是**循迹决定的**，这个符号只影响往哪边微移，所以从来没被真正验证过。
改成"强制旋转"之后，它成了硬约束 —— 而六边形在竖线的**左侧**、车往北走，
所以必须**向左**转。+1 把车转向背离六边形的一侧，转完脚下没有边线，位置环把它拽回来。

已改 `CFG_LOOP_EDGE_DIR = -1`。

> 这是"同一个变量换了一种用法，原来的隐含假设失效"的典型。写这类改动时，
> 必须回头问一句："这个符号以前是靠什么兜底的？"

### P0.5.2 顺带固化环岛速度

`CFG_V_LOOP_HEX 180 → 200`（与圆形环岛同速）。六边形边短（约 330 mm）、转角 60°，
太快会在每个顶点甩出去。先 200，稳了再在线加（`S 0 0 0 220 0`），标定好再固化。

**注意：`S`/`C`/`M` 这些运行时设置都存在 RAM，MCU 一复位就回默认值。**
今天实测复位过好几次（`run_224435`、`run_224740` 中途都出现 `[car] boot ok`），
所以凡是想长期生效的值，必须写进宏。

### P0.5.3 回退：入口改回横向偏置（用户现场判断优先）★

用户现场纠正（比我从日志推断更准）：

> "这一次才是转反了，刚刚是没转反的，但刚刚转完没找到线，就像是提前转了那样。
>   确实是转了 60 度，但要横向偏移才能找到线。你这改的还不如以前，因为以前我试的
>   时候都是稳定完赛，出错可能是概率问题，你改了逻辑反而没有成功过。"

**结论：回退。** `CFG_LOOP_ENTRY_DEG = 0`（回到 `e_bias` 横向偏置）、
`CFG_LOOP_EDGE_DIR = 1`（现场确认 −1 是反的）、`CFG_V_LOOP_HEX` 回 180（已验证值）。

回退的理由不只是"用户说不行"，而是**现象本身说明了机制**：
偏置方案不抢着转——它先把车往环岛那边挪一点，等传感器真的咬到六边形的那条边，
再由循迹去转。**时机是线给的**。而强制 60° 是程序抢跑：转的时候车还在往前走
（200 mm/s × 0.5 s ≈ 100 mm），等转完已经过了顶点，那条边早就不在车下了。

> **流程教训**：改动前先问"现在这套的成功率是多少"。能稳定完赛的方案，
> 不要因为"看起来不优雅"就去替换它；替换必须能解释清楚"为什么以前会失败"，
> 而"时灵时不灵"往往只是概率，不是设计缺陷。
