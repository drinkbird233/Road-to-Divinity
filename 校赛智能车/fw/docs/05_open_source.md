# 05 可用的开源项目与参考资料

版本：v0.1 / 2026-11-16
筛选原则：**只收录我实际打开验证过、或至少确认仓库存在的**；每条都写清"能不能直接用"。
（本环境访问 GitHub 直连受限，个别 GitHub 仓库是通过搜索结果确认存在、但未能逐文件核对，已单独标注。）

---

## 0 先给结论

对你这台车（F407 + 8 路数字循迹 + HWT101 + K230 + TB6612），开源生态的实际情况是：

| 类别 | 可用程度 | 说明 |
|---|---|---|
| **HWT101 官方 SDK** | ⭐⭐⭐⭐⭐ 直接用 | 维特智能官方 STM32 例程，解析逻辑不用自己写 |
| **上位机/波形工具** | ⭐⭐⭐⭐⭐ 直接用 | 决定你调参效率，投入产出比最高 |
| **K230 巡线例程** | ⭐⭐⭐⭐ 直接改 | 官方/01Studio 有完整可跑的 Python 例程 |
| **智能车元素状态机** | ⭐⭐⭐ 抄结构不抄代码 | 摄像头组的判据你用不上，但状态图值钱 |
| **逐飞/龙邱 MCU 库** | ⭐⭐ 只能看分层 | 都是 TC264/RT1064/CH32/龙芯，寄存器级，搬不到 F407 |
| **Arduino/QTR 循迹库** | ⭐ 别用 | 那是模拟量传感器，你是数字量，模型完全不同 |

**一句话：开源能帮你省掉"重复造轮子"，但省不掉"为你的车重新设计判据"。**

## 1 可以直接用的（建议今天就接上）

### 1.1 HWT101 → 维特智能官方 SDK

| | |
|---|---|
| 仓库 | <https://github.com/WITMOTION/WitStandardProtocol_JY901> |
| 文档 | <https://wit-motion.gitbook.io/witmotion-sdk/wit-standard-protocol/sdk/stm32_sdk-quick-start> |
| 适用 | WT61 / WT901 / WT931 / **HWT101（同属标准协议 0x55 系列）** |

**为什么值得用：** 核心文件 `wit_c_sdk.c` 已经把 0x55 帧、11 字节、累加和校验、0x51/0x52/0x53 帧分类
全部处理好了，对外暴露的是寄存器式索引（`AX / GX / YAW` 这种），比自己写状态机省一天。

**怎么接到我们的架构里（重要）：**

- ✅ **只用它的"帧解析 + 校验 + 取值"部分**；
- ❌ **不要用它的串口收发**（它假设阻塞式 `Usart2Init` + 中断回调），我们有 `bsp_uart.c` 的 DMA 环形缓冲；
- 把 `bsp_imu.c` 里 `bsp_imu_feed()` 的内部换成"喂给 `wit_c_sdk` 的 `WitSerialDataIn()`"，再在我们的 5 ms 里读 `s_reg[YAW]` / `s_reg[GZ]` 即可。

**顺带解决一个坑：** 文档里写了，模块支持发 `b\r\n` 自动扫描并切换波特率。
所以"9600 撑不住 100 Hz"这件事，用官方上位机或串口助手发一条命令就能改到 115200，不用重烧固件。

**注意：** HWT101 是单轴陀螺仪，帧里可能只有部分数据；拿 `YAW` 和 `GZ` 就够，别去读磁力计相关寄存器。

### 1.2 上位机波形工具（调参效率的决定性因素）

| 工具 | 链接 | 特点 | 建议 |
|---|---|---|---|
| **serialplot** | <https://github.com/zhiqiang-hu/serialplot>（原版）<br><https://github.com/any2fox/serialplot>（活跃分支，功能多） | 多通道实时波形，开源，支持二进制帧 | **首选**，免费、轻、能吃二进制 |
| **VOFA+** | <https://www.vofa.plus/docs/learning/> | 免费但不开源；FireWater/JustFloat 协议极简 | 想最快出波形就用它 |
| **逐飞助手** | <https://gitee.com/seekfree/seekfree_assistant> | 开源 C#，串口+虚拟示波器+摄像头图像 | 想改协议/加自定义解析可以读它源码 |
| **龙邱 LQ-Tool** | <https://gitee.com/lq-tech/LQ-Tool> | 开源，8 通道虚拟示波器 + TCP/UDP + 图传 | 同上 |

**建议组合：** 比赛用自定义 `0xAA55` 帧（已实现）；调试期在 `comm_task` 里加个 `CFG_USE_VOFA` 开关，
直接发 `speed_l,speed_r,yaw,err\n`，用 VOFA+ 的 FireWater 协议一秒出图。
**别浪费时间去解析自己的帧来看波形** —— 你会因为"看波形麻烦"而不看波形，然后靠猜调 PID。

### 1.3 K230 巡线（视觉部分）

| 资源 | 链接 | 内容 |
|---|---|---|
| 01Studio 教程 | <https://wiki.01studio.cc/docs/canmv_k230/machine_vision/color_recognition/line_follow/> | **完整可跑代码**：图像分 3 个 ROI，各自 `find_blobs` 找色块中心，按 0.7/0.3/0.1 加权求中心 X，再用 `atan((X-160)/120)` 算偏角 |
| CanMV 官方例程 | <https://github.com/kendryte/canmv_k230> | 官方 `resources/examples/` 下有 Machine / Vision / AI 各类例程 |
| 正点原子 K230 | <https://wiki.alientek.com/docs/Boards/Kendryte/DNK230D/example-image/line_follow/> | 黑线循迹实验，思路同上 |

**这套代码的价值不在"循迹"，在于它示范了我们文档里说的那个原则：**
**视觉只输出一个标量（偏角），不输出控制量。** 你把它改成输出"环岛入口是/否 + 目标横坐标"，
就是我们要的"第三票"。

**用法提醒：**
- 分辨率别超 320×240，否则帧率掉到 15 fps 以下；
- `find_blobs` 的灰度阈值 `(0, 64)` 要按你现场光照重标；
- 它的 `-atan(...)` 里的负号是"图像坐标 y 向下"造成的，接到我们 `target_x` 时符号要重新对一遍。

## 2 抄架构、不抄代码的

### 2.1 逐飞科技（SeekFree）

组织主页：<https://gitee.com/seekfree>（80 个公开仓库）

| 仓库 | 内容 | 对你有什么用 |
|---|---|---|
| `TC264_Library` / `RT1064_Library` / `CYT4BB7_Library` | 各平台 MCU 开源库 | **看分层**：`zf_device`（每个传感器一个文件，统一 `init/read`）+ `zf_driver`（外设）+ `zf_common`。和我们的 `bsp/` 是一个思路，可以对照命名和"设备不存在时怎么降级" |
| `TC264_Library` 里的 PID / 滤波 | 竞赛实战验证过的参数范围 | 我们的 `speed_ff ≈ 8`、`ki ≈ 60` 这类量级可以从他们的注释里交叉验证 |
| `seekfree_assistant` | 开源上位机 | 见 §1.2 |

**⚠️ 关键限制：逐飞没有 STM32F4 的库**（他们做 NXP / 英飞凌 / 兆易）。所以**不能直接搬**，
他们的代码是寄存器级 + 自家板级宏，移植成本比自己写高。

### 2.2 龙邱科技（LongQiu）

组织主页：<https://gitee.com/lq-tech>（26 个公开仓库）

| 仓库 | 内容 |
|---|---|
| `MicRail-Cart` | **第二十届智能车缩微电磁组资料合集**——赛道元素拆解、方案文档，是"别人怎么拆元素"的好样本 |
| `LQ-Tool` | 开源上位机（8 通道示波器） |
| `LQ-M0G3507_Library` | 基于 TI MSPM0 的库，但**代码风格刻意兼容 STM32 习惯**，可以看他们的驱动分层 |

### 2.3 一个具体的整车参考（含元素状态机）

| 仓库 | 内容 |
|---|---|
| <https://github.com/wuyou33/Smart-car> | 第十八届全国大学生智能车竞赛**三轮摄像头组**源码，README 明确写了包含：图像处理、位置式 PID、增量式 PID，以及**环岛、坡道、断路、避障**等元素的解决方案 |

> ⚠️ 本环境访问 GitHub 直连失败，这个仓库我**没能逐文件核对**，仅确认搜索结果显示其存在且描述如上。
> 你自己 clone 下来看一眼就知道值不值得抄。

**怎么用它：** 摄像头组的图像处理（二值化、边线提取、八邻域巡线）对你**完全没用**——
你只有 8 路数字量，没有边线。但它有三样东西值得抄：

1. **环岛状态图**：进 → 绕 → 出 几个状态、每个状态靠什么条件迁移；
2. **PID 的实现细节**：增量式 vs 位置式各自用在哪一环；
3. **"断路"（也就是你的盲走区）怎么处理**——他们的场景和你一样：一段没有线的路。

## 3 明确"不要抄"的清单

| 对象 | 为什么不要 |
|---|---|
| Arduino `QTRSensors` / 任何 QTR 库 | QTR 是**模拟量**（读 ADC 电压做加权），你是**数字量**（I2C 读 1 字节 8 位）。数学模型不同，抄了反而错 |
| 摄像头组的边线/八邻域算法 | 你没有边线信息，只有 8 个离散点 |
| 逐飞/龙邱的 TC264/RT1064 库 | 寄存器级 + 板级宏，移植成本 > 重写成本 |
| 任何"能跑就行"的阻塞式驱动 | 大部分开源代码在 `while()` 里等 I2C/串口，塞进 5 ms 控制环会直接毁掉实时性 |
| 年代久远的 StdPeriph 工程 | 和你的 HAL 工程混编是灾难 |

**开源代码最常见的三个坑（我审 `pin_plan.md` 时已经在你自己的方案里见过前两个）：**

1. **阻塞式外设访问**：`HAL_I2C_Mem_Read(..., 100)` 这种"100 ms 超时"在控制环里是定时炸弹。
2. **中断优先级不设或乱设**：抄来的 ISR 常带 `printf` 或长浮点运算。
3. **没有失效保护**：几乎没有开源项目会写"丢线 300 ms 停车"这种逻辑——而校赛恰恰靠这个拿分。

## 4 建议的"代码考古"流程（2 小时，只提三样东西）

不要 clone 一堆仓库然后开始读。按这个顺序，每项限时：

| 步骤 | 做什么 | 时长 | 产出 |
|---|---|---|---|
| 1 | 把 `WITMOTION/WitStandardProtocol_JY901` 的 `wit_c_sdk.c` 读一遍，只确认 **帧格式 + 寄存器索引表** | 30 min | 决定是否替换 `bsp_imu.c` 的解析 |
| 2 | `wuyou33/Smart-car` 只找"环岛"相关的那个函数，**画出它的状态迁移图**（不读实现细节） | 30 min | 对照你的 `EL_LOOP_*` 少了哪个状态 |
| 3 | 跑通 serialplot 或 VOFA+，把 `speed_l/speed_r/yaw/line_err` 四路画出来 | 40 min | **这是本轮最值钱的产出** |
| 4 | 其余仓库只 star 不读 | 20 min | 以后遇到具体问题再定向查 |

**别做的事：** 花两天读完逐飞的 TC264 库然后发现搬不过来。

## 5 我建议的取舍

如果只让我选三个开源项目用在这台车上：

1. **维特智能 WIT SDK** —— 替掉手写的 IMU 解析（真实节省 1 天）
2. **serialplot / VOFA+** —— 决定你能不能看见 PID 在干什么（节省 3 天以上的盲调）
3. **01Studio 的 K230 巡线例程** —— 视觉侧的起点（节省 1–2 天）

其余全部归类为"遇到具体问题时再去定向查"，包括逐飞和龙邱的整车库。
